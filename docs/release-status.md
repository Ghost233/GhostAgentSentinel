## 发布流程与完成条件

### 发布前

发布使用当前本地 `main`。测试与真实宿主验收在本地 macOS arm64 完成。先按 [开发与验证](../README.md#开发与验证) 准备锁文件依赖及已构建的 DSH SDK，按变更影响完成必要的 `npm run check`、`npm test` 和 `npm run test:resources`。记录源码版本、验证命令和真实退出码；本地必要检查通过后才提交和推送。输入、环境及覆盖范围未变的成功证据可复用。本地缺口保持未完成，不转交 GitHub Actions；已知失败先修复。

仅调整 workflow 及对应发布文档时，只核对 workflow 配置并运行 `npm run release:check`，不重复完整测试、安装或界面操作。随包文档变化时重新生成安装包和哈希清单，运行代码与依赖未变的本地证据继续有效。

每次发布记录两端安装产物与最终源码的对应关系、受影响功能及交付复核。实机范围按本页所列证据和未验项公开说明，不把发布状态当作全部产品验收通过。本轮未执行的升级专项不得记为通过。旧证据只在输入与环境未变且不受本次修改影响时复用。

发布前确认实际打包 workflow、版本 tag 和预期资产清单。GitHub Actions 只使用 macOS arm64 生成安装包、核对版本／文件清单／哈希并上传产物，不运行 `npm test`、`test:chatgpt`、`test:resources` 或真实宿主验收。资产至少包括对应版本的 `.tgz` 安装包、`SHA256SUMS` 和验证报告。正式 Release 继续使用既有发布方式，打包 workflow 不增加自动发布步骤。

### 发布后

以下条件全部满足，才可报告发布完成：

- 本地检查：必要检查已在 macOS arm64 通过，或有输入与覆盖未受影响的有效证据。本地未验项目逐项保留。
- 远端打包：对应发布 tag 和实际提交的打包 run 已完成，结论为 `success`。不要求远端测试全部成功；历史测试失败保持失败，不回填通过。打包排队、取消、跳过、失败或缺少证据仍为未完成。
- Release：对应 tag 的正式 Release 已创建，既非草稿也非预发布；tag、包版本和 Release 版本一致，tag 指向实际发布提交。
- 远端资产：通过 Release 的资产列表核对预期清单，名称和版本正确，资产齐全且大小均大于零。构建及资产校验结果以对应成功的 Actions 记录为依据。
- 本地同步：先更新涉及的本地分支，再从对应本地分支推送。远端更新后，以 fast-forward 同步所有涉及的本地分支，并核对本地与远端 tag 的对象及解引用提交一致。结束前检查当前工作区状态，记录各对应分支和 tag 的完整提交哈希；对应引用须一致，当前分支不得落后。多个目标分支应保持同一提交时，逐一核对同一完整哈希。

同步遇到分叉、tag 冲突或用户文件阻碍时，报告具体引用和阻塞文件并停止。用户未明确授权时，不自动 stash、移动、删除或覆盖用户文件，也不强制改写引用。

发布后默认只读取远端状态和资产元数据。下载发布资产到本地、重新计算哈希、安装或运行，仅在用户另行明确要求时执行，不作为默认发布完成条件。交付时给出 Actions、Release 链接和本地同步结果；缺少任一完成条件时，明确列出未完成项。
